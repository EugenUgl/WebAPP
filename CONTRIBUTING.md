# 🛠 Правила разработки (Contributing Guidelines)

Этот документ описывает глобальные стандарты и правила микросервисного проекта. Правила, специфичные для конкретного языка программирования или фреймворка, описаны в документации каждого отдельного сервиса (в папке `docs/services/`).

---

## 1. Архитектурные правила (Microservices Rules)

1. **Единственная точка входа**: Клиент (браузер) общается с системой **только** через `gateway`. Внутренние сервисы (`auth-backend`, `frontend-service`) не должны пробрасывать порты наружу (`ports`) в `docker-compose.yml`.
2. **Изоляция данных (Database per Service)**: Каждый сервис имеет свою базу данных. Запрещено подключаться к базе данных другого микросервиса напрямую. Общение происходит только через API или события.
3. **Полиглотность (Polyglot Architecture)**: Сервисы могут быть написаны на любых языках программирования и использовать любые фреймворки, если это оправдано задачей.
4. **Слабая связанность (Loose Coupling)**: Издатель события не должен знать, кто и сколько сервисов на него подписано. Добавление нового подписчика не должно требовать изменения кода издателя.
5. **Контракты**: Любое изменение HTTP-маршрутов или схемы событий (Payload в брокере) должно быть отражено в `docs/contracts.md`.
6. **Именование событий**: Subject в брокере сообщений формируется по паттерну `сущность.действие` (например, `user.registered`, `user.deleted`, `order.created`).

---

## 2. Общие правила кода (Global Coding Style)

1. **Форматирование**: В каждом сервисе должен использоваться стандартный для выбранного языка линтер/форматтер (например, `Black` и `Ruff` для Python, `Prettier` и `ESLint` для JS, `gofmt` для Go).
2. **Именование**: Строго следуем официальным конвенциям выбранного языка (например, `snake_case` для Python, `camelCase` для JavaScript/Java, `PascalCase` для классов).
3. **Безопасность**: 
   * Никаких паролей, API-ключей и секретов в открытом виде в коде. На этапе разработки они передаются через переменные окружения (в будущем — через `.env`).
   * Пароли пользователей хранятся **только** в виде криптографических хешей.
4. **Логирование**: Вместо вывода в консоль (например, `print()` или `console.log()`) используйте встроенные механизмы логирования выбранного языка/фреймворка (например, `logging` в Python).

---

## 3. Правила работы с Docker

1. **Базовые образы**: Используем легковесные образы (например, `-slim` или `-alpine`). Никогда не используем тег `latest` для базовых образов, чтобы сборки были воспроизводимыми.
2. **Кеширование слоев**: В `Dockerfile` сначала копируем файлы зависимостей (`requirements.txt`, `package.json` и т.д.), устанавливаем их, и только потом копируем исходный код (`COPY . .`). Это ускоряет пересборку.
3. **Сетевые имена**: Сервисы общаются друг с другом по именам из `docker-compose.yml` (например, `http://auth-backend:5000`), а не по IP-адресам.

---

## 4. Правила работы с Git (Git Workflow)

1. **Ветвление**:
   * `main` — стабильная ветка. Прямые пуши запрещены.
   * `feature/название-фичи` — для новой функциональности.
   * `bugfix/название-бага` — для исправления ошибок.
   * `docs/что-обновили` — для правок документации.
2. **Формат коммитов (Conventional Commits)**:
   Сообщение коммита должно иметь префикс, указывающий на тип изменений:
   * `feat: add user logout route`
   * `fix: resolve redirect loop in gateway`
   * `docs: update API contracts`
   * `refactor: move event logic to separate module`
   * `chore: update docker base images`
3. **Пул-реквесты (PR)**: Перед слиянием в `main` код должен успешно собираться (`docker compose up --build`).

---

## 5. Документация и актуализация (Documentation & Definition of Done)

Документация — это часть кодовой базы. Любое изменение архитектуры без обновления документации считается **незавершенной задачей** (не passing Definition of Done). Пул-реквесты с устаревшей документацией не принимаются.

### 5.1. Внедрение нового микросервиса
При добавлении нового сервиса (контейнера) в архитектуру **обязательно** требуется:
1.  Создать файл описания сервиса в `docs/services/<имя-сервиса>.md`. В нем должны быть:
    *   Назначение и зона ответственности сервиса.
    *   Технологический стек и локальный Coding Style.
    *   UML-диаграммы (Class, Sequence) для ключевых сценариев.
2.  Обновить общую структуру проекта и UML-диаграммы компонентов/развертывания в `docs/architecture.md`.
3.  Добавить новый сервис в `docker-compose.yml` и описать его зависимости (например, `depends_on`, `networks`).
4.  Если новый сервис подписывается на события или публикует их, обновить раздел событийных контрактов в `docs/contracts.md`.

### 5.2. Изменение контрактов или архитектуры существующих сервисов
При любом изменении взаимодействия (API или события) **обязательно** требуется:
1.  **HTTP API:** Если меняются пути, методы или структура запросов/ответов, обновить таблицу HTTP-контрактов в `docs/contracts.md`.
2.  **События (NATS/Брокеры):** Если меняется имя события, его Payload или Stream, обновить раздел событийных контрактов в `docs/contracts.md`.
3.  **UML:** Если изменение повлекло за собой новые вызовы или изменило порядок взаимодействия, обновить соответствующие **Sequence-диаграммы** в документации затронутых сервисов и в `docs/architecture.md`.
4.  **Обратная совместимость:** При изменении контрактов учитывать обратную совместимость. Если поле удаляется или переименовывается, это должно быть явно задокументировано как *Breaking Change*.

### 5.3. Общие правила оформления документации
1.  Все UML-диаграммы пишутся исключительно в формате **Mermaid.js** прямо внутри Markdown-файлов (без внешних картинок).
2.  Все файлы документации хранятся в папке `docs/`.
3.  Документация должна быть читаемой и структурированной, с использованием заголовков и списков.
